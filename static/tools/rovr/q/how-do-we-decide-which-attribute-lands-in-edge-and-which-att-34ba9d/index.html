How Attributes Are Decided Between Edge Profiles and Profile Hub in AEP

Great question. The decision of which attributes land on the Edge Network versus staying in the Profile Hub is governed by a combination of merge policies, projection configurations, and the nature of the use case. Here's a breakdown:

1. The Core Architectural Distinction

| | Profile Hub | Edge Network |

|---|---|---|

| Purpose | Thoroughness & completeness | Speed & real-time |

| Data type | All historical data, rich profile context | Lightweight — only what's needed for personalization |

| Use cases | Batch/streaming segmentation, destinations, identity graph | Real-time personalization, edge segmentation |

| Processing | Batch and streaming workflows | Behavioral/event-driven, real-time |

The Edge Network only retains the audience memberships, profile identities, and attributes necessary for personalization — it is not a full copy of the hub profile.

2. What Controls Which Attributes Go to the Edge?

Active-On-Edge Merge Policy

The primary control mechanism is the Active-On-Edge merge policy. You must configure a merge policy with the Active-On-Edge setting enabled. This merge policy determines which profile data is projected out to the edge nodes. Only attributes governed by this merge policy will be available on edge profiles.

Projection Destinations & Projection Configurations

Data is routed to a specific edge via projections. A projection destination defines which edge (geographic node) the data will be sent to. The projection configuration determines what data gets sent. Only attributes explicitly included in the projection are replicated to edge profiles — everything else remains in the hub.

Custom Personalization Destination

When setting up real-time personalization use cases, you configure a Custom Personalization connection that specifies which profile attributes should be sent to the Edge Network. Only the attributes you select in that connection configuration will be available at the edge for decisioning and personalization.

3. Decision Framework: Edge vs. Hub

Use this framework to decide where an attribute belongs:

| Criteria | Send to Edge | Keep in Hub Only |

|---|---|---|

| Needed for real-time personalization? | ✅ Yes | ❌ No |

| Needed for next-click/same-session decisions? | ✅ Yes | ❌ No |

| Heavily historical / aggregate data? | ❌ No | ✅ Yes |

| Used in batch segmentation only? | ❌ No | ✅ Yes |

| Sensitive/compliance-restricted data not needed at edge? | ❌ No | ✅ Yes |

| Propensity scores or AI insights needed for on-site targeting? | ✅ Yes | ❌ (can stay in hub too) |

4. Practical Use Cases That Require Edge Attributes

  • Real-Time Personalization: Attributes like `loyalty_tier`, `preferred_language`, or `last_product_viewed` that drive on-site content decisions need to be at the edge for low-latency retrieval.
  • Customer Support: Attributes like `account_status` or `recent_interaction` need to be pulled in real-time via the Edge Network API when a customer contacts support.

5. Key Takeaway

The edge profile is intentionally lightweight by design. You should only project attributes to the edge that are directly required for real-time, time-sensitive personalization or decisioning. All other rich profile data — historical events, identity graphs, complex segments computed in batch — lives in the hub and is accessed through non-real-time workflows.

The levers you control are:

1. Active-On-Edge merge policy — enables edge projection

2. Projection configuration — defines what attributes are included

3. Custom Personalization destination — surfaces specific attributes to the Edge Network for use in downstream real-time applications
