Comparing Streaming Schema Data with Batch Schema Data in a Streaming Audience

Short Answer: Not Directly — But It Is Possible via Segment of Segments

What Changed (Important Update)

Prior to a recent platform update, you could create a streaming audience definition that combined both batch and streaming data sources directly.

However, with the latest update:

> Creating an audience with both batch and streaming data sources will now be evaluated using batch segmentation — not streaming segmentation.

How to Achieve This While Keeping Streaming Evaluation

If you need a segment definition evaluated using streaming or edge segmentation that combines both data types, you must follow this approach:

Step-by-Step Approach: Segment of Segments

Prerequisites:

  • One audience built on a Profile schema (batch source)
  • One audience built on an Experience Event schema (streaming source)
  • The batch ruleset must be based on a profile schema

Step 1: Create the Batch Audience (Profile Schema)

Build your batch audience separately. For example:

| Audience | Schema | Source Type | Query Definition |

|---|---|---|---|

| California Residents | Profile | Batch | Home address is in the state of California |

Step 2: Create the Streaming Audience (Experience Event Schema)

Build your streaming audience separately. For example:

| Audience | Schema | Source Type | Query Definition |

|---|---|---|---|

| Recent Checkouts | Experience Event | Streaming | Has at least one checkout in the last 24 hours |

Step 3: Combine Using Segment of Segments

Create a third audience that references both using `inSegment()` logic combined with streaming event rules:

```

inSegment("e3be6d7f-1727-401f-a41e-c296b45f607a") and

CHAIN(xEvent, timestamp, [C0: WHAT(eventType.equals("commerce.checkouts", false))

WHEN(<= 24 hours before now)])

```

  • The `inSegment()` call references the batch audience by its Audience ID
  • The `CHAIN` expression handles the streaming event condition
  • The resulting audience will be evaluated using streaming segmentation because it leverages batch audience membership by reference rather than directly mixing data sources

Key Rules to Remember

| Scenario | Evaluation Method |

|---|---|

| Streaming data only | Streaming segmentation ✅ |

| Batch data only | Batch segmentation ✅ |

| Batch + Streaming combined directly | Forced to batch segmentation ⚠️ |

| Batch audience referenced via `inSegment()` + Streaming event rules | Streaming segmentation ✅ |

| Two event-based audiences combined | Must use `inSegment()` for both — cannot just combine two events directly |

Additional Important Note

> If you want to combine two audiences that both contain event data, you cannot simply combine the two events in one rule. You must:

> 1. Create each as a separate audience

> 2. Create a third audience that uses `inSegment()` to refer to both

Summary

You cannot directly compare streaming schema data with batch schema data in a single streaming audience rule without losing streaming evaluation. The correct approach is to separate the concerns into individual audiences and then combine them using Segment of Segments with `inSegment()`, which preserves streaming segmentation evaluation.
