SPA vs. Normal Websites in Adobe Target: VEC Implementation & Data Analysis

Great question — SPA (Single-Page Application) websites behave fundamentally differently from traditional multi-page websites, and this has significant implications for both Target activity implementation and data analysis.

Why SPAs Are Different

On a traditional website, every page navigation triggers a full page reload, which means:

  • The browser makes a new HTTP request
  • at.js / Web SDK fires automatically on each new page load
  • Target mboxes and analytics beacons fire naturally per page

On a Single-Page Application (SPA), the page never fully reloads. Instead:

  • JavaScript dynamically rewrites the DOM (React, Angular, Vue, etc.)
  • The URL may change (via `history.pushState`) but no full page reload occurs
  • at.js and analytics libraries do not automatically re-fire on view changes
  • Target has no native awareness that a "new page" or "new view" has been presented to the user

Implementation Differences

Traditional Website

  • Drop at.js or Web SDK on every page via a global header tag or Tags (Launch) rule
  • Target fires a global mbox on page load automatically
  • VEC works out of the box — it loads the URL and the DOM is stable

SPA Website

1. You Must Use the SPA VEC (not the standard VEC)

The standard VEC assumes a stable DOM tied to a URL. SPAs have dynamic DOM changes without URL reloads, so Adobe Target provides a dedicated SPA Visual Experience Composer that works with the concept of Views.

2. The Concept of Views

A View is a logical group of visual elements that together make up a SPA experience — it could be:

  • An entire "page" (e.g., the checkout page rendered without reload)
  • A specific component (e.g., a hero banner that changes on tab click)

You define Views in your codebase explicitly.

3. `triggerView()` — The Critical Implementation Call

With at.js 2.x, you must instrument your SPA code to call `triggerView()` whenever a new View is rendered:

```javascript

adobe.target.triggerView('checkout-step-1');

```

This tells Target:

  • "A new View has been displayed — apply any activities targeting this View"
  • It also fires analytics beacons for that View (critical for reporting)

Without `triggerView()` calls, Target activities will not render on SPA view changes.

4. Web SDK Equivalent

If using the Experience Platform Web SDK, you send a `sendEvent` with `type: "decisioning.propositionDisplay"` or use the `renderDecisions` flag appropriately when views change — the concept is the same as `triggerView()` but via Web SDK syntax.

5. VEC Authoring Difference
  • In the SPA VEC, you author experiences per View, not just per URL
  • You can navigate to different Views within the SPA VEC using the Views panel
  • Activities can target specific Views, meaning an experience only renders when that View fires

Data Analysis Differences

Traditional Website Reporting

  • Each page load = a natural visit/hit boundary
  • Activity entry, impressions, and conversions are straightforward to attribute per page
  • Analytics for Target (A4T) works cleanly because each page load fires both an Analytics beacon and a Target call

SPA Reporting Challenges & Considerations

1. Activity Impressions Tied to `triggerView()`
  • A visitor is only counted as entering an activity when the targeted View fires via `triggerView()`
  • If `triggerView()` is not called (or called with the wrong View name), impressions will be under-reported
2. A4T (Analytics for Target) in SPAs
  • A4T requires both a Target request and an Analytics beacon to fire together for proper stitching
  • In SPAs, you must ensure that when `triggerView()` fires, the corresponding Analytics page view or custom link call also fires for the same View
  • If they are out of sync, you will see inflated or missing visits in A4T reports
  • Adobe recommends using the supplemental data ID (SDID) stitching or the Web SDK with the Edge Network to handle this more reliably
3. Page View Inflation / Deflation Risk
  • If `triggerView()` is called too many times (e.g., on every minor component render), you may over-count activity impressions
  • If it's not called on meaningful View transitions, you will under-count
  • Governance of where and when `triggerView()` is called is critical for data quality
4. Conversion Metrics
  • Conversion events (clicks, form submits, custom events) work similarly to traditional sites — they use Target click-tracking or `trackEvent()` calls
  • However, since the DOM is dynamic, click-track selectors must be carefully validated — elements may be re-rendered and selectors can break
5. Visit/Visitor Counting
  • In a SPA, a visitor could trigger many Views in a single session — this is normal
  • Make sure your reporting metrics (impressions, conversions) align with how your business defines a meaningful interaction, not just DOM renders

Quick Comparison Summary

| Dimension | Traditional Website | SPA Website |

|---|---|---|

| Target fires on | Every page load (automatic) | `triggerView()` calls (manual) |

| VEC type | Standard VEC | SPA VEC |

| Authoring unit | Page URL | Named Views |

| A4T stitching | Automatic per page load | Must synchronize beacons manually |

| Implementation risk | Low | Higher — requires dev instrumentation |

| Impression counting | Per page load | Per `triggerView()` call |

| DOM stability | Stable on load | Dynamic — selectors can break |

Key Takeaway

The biggest shift from traditional to SPA Target implementation is that you are no longer relying on the browser's natural page lifecycle — instead, your development team must explicitly tell Target (via `triggerView()`) when a meaningful user experience has changed. Getting this instrumentation right is the foundation for both accurate activity delivery and trustworthy reporting data.
