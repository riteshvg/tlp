Visitor Identity Stitching from React Native to WebView in AEP

The Problem

When a user navigates from the native portion of your React Native app into an in-app WebView, Adobe Experience Platform generates separate ECIDs for each context. This results in:

  • Disconnected hits between native app events and WebView events
  • Inflated visit and visitor counts
  • Fragmented customer profiles in AEP

How the Solution Works

To unify the identity across both surfaces, you need to pass the user's ECID from the native app layer into the WebView. The AEP Edge Identity extension used within the WebView:

1. Collects the current ECID from the URL (passed by the native layer)

2. Adds it to outgoing requests instead of requesting a new ID from Adobe

3. This ensures both the native app and WebView share the same ECID, keeping the profile unified

Implementation Overview

Prerequisites

  • React Native app with AEP Mobile SDK integrated
  • WebView component in your React Native app
  • AEP Edge Identity extension installed in both the native and WebView contexts

React Native SDK Compatibility

Ensure you are using compatible versions of the AEP Assurance and MobileCore packages:

| AEP Assurance Version | Mobile Core Version | Install Command |

|---|---|---|

| `react-native-aepassurance` v2.x.x | `react-native-acpcore` | `npm install @adobe/react-native-aepassurance@^2.0.0` |

| `react-native-aepassurance` v3.x.x | `react-native-aepcore` | `npm install @adobe/react-native-aepassurance@^3.0.0` |

> ⚠️ Important: `react-native-acpcore` is only compatible with `react-native-aepassurance` v2.x.x and below. Mixing versions will cause build errors such as:

> ```

> RCTAEPAssurance: Fatal error: Module 'AEPAssurance' not found

> ```

> or

> ```

> AppDelegate: AEPAssurance.h file not found

> ```

> If you hit this, downgrade with:

> ```shell

> npm install @adobe/react-native-aepassurance@^2.0.0

> ```

Step-by-Step Implementation

Step 1: Retrieve the ECID from the native React Native layer

Use the AEP Edge Identity extension API to fetch the current ECID from the native SDK before loading the WebView.

Step 2: Append the ECID to the WebView URL

Pass the ECID as a URL parameter when constructing the WebView URL. The AEP Edge Identity extension within the WebView is designed to read this parameter from the URL automatically.

Step 3: Initialize the WebView with the identity-enriched URL

Load the WebView using the URL that now contains the ECID. The Web SDK (alloy.js) running inside the WebView will detect the ECID in the URL and use it instead of generating a new one.

Step 4: Validate identity stitching

Use the Adobe Experience Platform Debugger (Chrome extension) or AEP Assurance to confirm:

  • The same ECID appears in both native app events and WebView events
  • No duplicate profiles are created in AEP
  • The identity graph shows both identifiers (e.g., ECID + CRMID if the user is authenticated) linked to a single profile

Verifying Identity Stitching in AEP

Once implemented, validate the stitching:

1. Log in to Adobe Experience Platform

2. Navigate to Customer → Profiles → Browse

3. Search by ECID or CRMID

4. Open the profile and check the Identities section — you should see both the ECID (from the native/WebView layer) and any authenticated identifier (e.g., CRMID) linked together

5. Confirm no duplicate profiles exist for the same user

You can also use the AEP Debugger to inspect outgoing Web SDK (`alloy.js`) requests from the WebView and verify the ECID value matches what was passed from the native layer.

Supported SDK Languages

Adobe provides dedicated SDKs for mobile data collection relevant to this use case:

| Platform | Language |

|---|---|

| Android | Kotlin |

| iOS | Swift |

| Cross-platform (including WebViews) | React Native |

If neither the Mobile SDK nor Web SDK fits a particular part of your architecture, you can use the Adobe Experience Platform Edge Network API to send data directly to AEP.

Key Takeaway

The core principle is: the native app owns the ECID and passes it to the WebView via URL parameter. The WebView's AEP SDK then reuses that ECID rather than minting a new one, ensuring a single continuous identity thread across the entire in-app experience.
